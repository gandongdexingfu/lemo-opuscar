# 通用規範（所有影片類型共用）

底座：lemo-opuscar（本倉庫）。開工時按順序讀：本文件 → `mine/routes/` 對應路線 → opuscar 的 `DIRECTOR.md`、`TECHNIQUE.md`、選定風格的 `styles/<slug>/STYLE.md`。
本文件與 opuscar 衝突時，**以本文件為準**（例如：我們允許用戶擁有權利的 AI 生成圖、預設直式 9:16）。

## 用戶偏好
- 預設中文回覆、簡潔；任務有明顯錯誤要先指正。
- 開工前：問清需求 → 判斷工具能否完全做到 → 能做到說明做法後開始；做不到或沒把握先做風險評估（問題、替代方案、耗時、token），由用戶決定。
- 先在雲端做；不在用戶 Mac 上安裝無關軟體、不產生不必要的檔案。
- 路線是**代碼動畫**，不用 AI 視頻模型（太貴）。可用 ChatGPT 生靜態圖（用戶擁有權利，opuscar DIRECTOR §12 允許用戶提供的素材）。
- 先做小測試（約 5–10 秒）確認審美，再做完整版。
- 預設直式 1080×1920（抖音、小紅書）；opuscar 工具一律加 `--size 1080x1920`。

## 精品標準（2026-10-11 定，每支片開工前先讀、交付前逐條對照）
用戶的預設要求是「越細越好、務必精品」；以下四條沒有例外，不因時間、篇幅、改版次數而打折。
1. **資料要挖完**：主要來源（官方規格、拆機照片、文獻）要逐張、逐項盤點，再找第二來源交叉比對（如 FCC 內部照片、其他拆機、晶片分析）。每個細節標明出處；查不到的標「證據不足」，不憑感覺補。先交「零件／資料清單」給用戶確認，再開始畫。
2. **工具要用足**：選定的引擎與技能要用它最好的能力，不用自寫的簡化版代替（例：Anatomy 的曲面用 `lathe` 平滑明暗、線纜用 `tube`、幾何用 `audit` 驗到零錯誤、4 倍放大逐一檢查接點）。
3. **任何降級取捨都先告訴用戶**：凡是「少做、簡化、改用近似、跳過某個來源或工具」的決定，動手前先說明原因與代價，由用戶決定；不能自己決定後默默做。
4. **交付時列出「沒做到的部分」**：每次交付除了成果，還要列出：沒用上的資料、沒用上的工具能力、證據不足而示意或省略的地方、已知瑕疵。

## 參考片拆解
- `mine/tools/breakdown.py`（取自 huashu-art-motion）出接觸表、切點、節拍網格、運動熱圖；`ffmpeg showspectrumpic` 看音軌。
- 先判斷是 AI 視頻還是代碼可做（暫停一幀，像照片→不適合純代碼；像畫/設計稿→適合）。
- **用 opuscar 標準打分**（每項 0–2 分，附秒數證據），拆解報告最後列「值得學的 3 件事」與「我們能用代碼做到的程度」：
  1. 鉤子：前 3 秒有沒有讓人停下來的畫面或問題
  2. 結構：主體、目標、轉折是否清楚；結尾有無呼應
  3. 節奏：有無快慢交替、明顯加速或減速、喘息停頓
  4. 運鏡：幾種運鏡與景別；有無招牌鏡頭；轉場是否用媒材本身完成
  5. 招牌時刻：情緒高峰有沒有「只有這種媒材做得到」的一刻
  6. 字卡：停留時間是否達到 字數÷4.5+1.5 秒；位置是否避開平台按鈕
  7. 聲音：三層是否齊全；安靜段幾次；聲音轉場幾次；音樂與剪輯是否對拍

## 導演方法（吸收自 opuscar DIRECTOR.md）
- **先寫 TREATMENT.md 再動手**：三種候選結構→選一並說明理由；一句話 logline；起承轉合；**標竿作品**（學什麼／不學什麼）；分鏡表（景別、角度、運鏡、時長、為什麼）；逐秒節拍表；cue map（速度、小節、每個剪輯與動作落在哪拍）；聲音設計表；字幕／字卡設計。
- **故事**：一個主體、一個目標、一個轉折；前 3 秒要有鉤子（不要慢吞吞的片頭）；結尾要呼應（首尾呼應、揭示規模、或第二次做對）。
- **一個「媒材原生」的招牌時刻**放在情緒高峰（例：光的演變的「燈光縮成地球上的城市燈火」）。
- **節奏**：快慢交替、一次明顯加速或減速、一次讓觀眾喘息的停頓；全片同一速度＝失敗。
- **運鏡**：至少四種不同運鏡與景別變化（推、拉、平移、視差、焦點轉移）；一個讓人記住的招牌鏡頭；轉場用媒材本身完成，不用預設淡化與硬切。
- 關鍵時刻主體至少佔畫面高度 1/3；不要太暗、不要同色疊同色、字幕不要蓋住主體。
- **不要照抄示範片**：opuscar 的 DEMO 只在寫完 TREATMENT 後才看，學技術不學故事；結構、開場、招牌鏡頭、運鏡路線、配樂形狀、結尾六項至少四項不同。

## 字卡與字幕停留（opuscar 公式，必須遵守）
- 文字動畫結束後，至少停：**中文 = 字數 ÷ 4.5 + 1.5 秒**；英文 = 字母數 ÷ 15 + 1.5 秒。
  - 例：光的演變每張字卡約 16 字 → 需約 5.1 秒完整停留（我們 v2 只停約 3 秒，偏短）。
- 字幕每句至少 1.8 秒，且不短於語音長度 + 0.6 秒；標題卡至少 4 秒。
- 頁面提供 `window.TEXTS(t)` 後，可用 `core/render/readcheck.mjs` 自動檢查。
- 直式短片：重要文字放畫面高 15%–80% 之間，避開平台頂部與底部按鈕區。

## 生圖（嚴格把關，不合格就返工）
- **讓照片裡的部件動起來**（扇葉轉、門打開…）：請 ChatGPT 以原圖編輯出「去掉那個部件」的版本（對位要 0 px），兩張相減就分出部件層；動畫＝底圖＋變換後的部件層＋蓋回前景（輪轂、鋼絲）。旋轉要按透視：先把橢圓拉成圓再轉再壓回去。範例：`films/taiwan-sparrow` 的電扇。
- 寫實、精緻；同一支片先定一張基準圖，其餘都用它當參考圖保持背景、機位、打光一致。
- 需要前後狀態的（點燈/熄燈、前/後）：第二張用第一張做 edit（keep EVERYTHING identical…），再用相位相關檢查對齊（偏移應 0 px）。
- 逐張檢查：無變形（手、文字、結構）、史實/事實準確、與前後一致、物件有細節不普通。重要的可一次生 2 版挑。
- 生圖工具回應逾時常常其實已完成：先列檔案再決定是否重生。
- 綠幕摳圖：alpha 由 g−max(r,b) 計算；鏤空處（把手、腿間）不要被填洞；只在邊緣去綠溢色。

## 畫面與動作
- 從容：進場、退場都要完整；結尾緩緩收尾，只要一個結局。
- 不做不逼真的動作（例：照片位移模擬的劃火柴）→ 改用音效交代，只讓會自然動的東西動。
- 動作要有預備、動作、跟隨；姿勢用關鍵幀＋緩動過渡，不要在 if 裡瞬切。
- 字卡風格範例：博物館說明牌（細金線＋菱形、年份逐字、中文大標逐字由模糊到清晰、英文小型大寫、關鍵詞以｜分隔），字體 Noto Serif CJK TC；英文單字整體排，不拆字母。

## 聲音（吸收自 opuscar）
- **三層**：環境音、動作音效（每個看得見的動作都要有聲音，材質要對）、音樂；對白與關鍵音效時壓低音樂。
- **至少兩次真正的安靜**，放在轉折或情緒高峰前；安靜後的第一個聲音要是全片最重要的聲音之一。
- **至少兩次用聲音做轉場**（下一場的聲音提前進來，或上一場的聲音延續過剪輯點）。
- **配樂**：畫面有很多卡點（停頓、逐拍動作、標題）時，**首選 sampler**；只要整首鋪底、不卡點時才用 Gemini。
  1. opuscar 的 `core/audio/sampler.py`（**首選**）：我寫譜，用免費 CC0 真實樂器取樣演奏，每個音精準到毫秒，安靜段能切到連殘響都沒有。在雲端下載樂器庫（`sh tools/fetch.sh instruments vcsl`、`freepats`），用戶 Mac 不裝任何東西。範例：`films/taiwan-sparrow/score.py`（烏克麗麗、竪笛、木琴、鐘琴、馬林巴、沙鈴、木魚）。畫面也可以反過來配合音樂，把關鍵動作挪到拍點上。
  2. 用戶用 Gemini 生成：**做不到指定總長和秒數**（要 33 秒常給 55 秒）。只適合整首直接用，不剪（光的演變就是整首延後 2 秒進場）；或當沒有旋律的氛圍底音，任意截取。**不要把不同段落剪接在一起**，接點一定聽得出硬切。
  3. numpy 合成：只適合氛圍、音效、晶片音樂。
  - 不要通用的「鋼琴＋弦樂」，用風格對應的樂器；低頻（20–120 Hz）不要過重。
- 音效：opuscar 的 `core/audio/sfx.py` 或自己用 numpy；殘響 IR 必須先低通，否則有嘶聲；另存「純音效」軌方便換配樂。
- **響度 −14 LUFS**：`core/render/mux.sh` 在雲端每次都誤報「音檔只解出 N 秒、檔案損壞」（它讀 ffmpeg 進度的方式有問題，檔案其實完好），改用手動：`ebur128` 量響度 → `volume` 補差值 → `alimiter` 限幅，顆粒用 `noise=alls=3:allf=t`。指令見 `films/taiwan-sparrow/build.sh`。

## 渲染與交付
- 畫面是時間的函數：頁面提供 `window.DUR`、`window.render(t)`、`window.READY`（可選 `window.EV` 事件、`window.TEXTS`）；全部確定性（亂數要種子），任一幀可單獨渲染。
- **渲染用 opuscar 工具**：`node core/render/still.mjs` 出靜幀檢查；`node core/render/video.mjs <工程> --fps 24 --workers 3 --size 1080x1920`（JPEG 截圖、多執行緒，比我們舊的單執行緒 PNG 快很多）；**顆粒感交給 ffmpeg 加**，不要畫在頁面裡（會讓每幀難壓縮又慢）。
- 交付前檢查：接觸表兩輪、關鍵動作 0.2 秒條帶、`ffmpeg -af ebur128`（響度）、`blackdetect`（黑幀）、全速帶聲音看一遍。
- 交付物：成片 mp4、`poster.jpg`、`.srt`（有字幕時）、`TREATMENT.md`、`CREDITS`（第三方素材、樂器庫、字體的來源與授權）、可一鍵重建的 `build.sh`。
- 傳回用戶電腦單檔上限 30MB：超過用 `-crf 24 -preset slow` 重壓。
- 每次交付：SendUserFile ＋ 寫回用戶資料夾，說明改了什麼、自己看到的問題。

## 發布
- 抖音、小紅書文案用簡體；必須勾選「含 AI 生成內容」。封面選最搶眼的一幀。

## 素材與成片的存放
- 代碼、文字進倉庫 `mine/`；照片、影片、音樂放 GitHub Releases（每支片一個 tag，例 `light-evolution-v1`），不進 git 歷史。
- 本 session 無法建立 Release：在用戶電腦把素材打包成 zip，請用戶在網頁 Releases → Draft a new release 拖入上傳。
- **上傳的檔名要用英文**：GitHub 會把中文字元去掉（例：`光的演變_完整版v2_配樂2.mp4` 變成 `_.v2_.2.mp4`）。
